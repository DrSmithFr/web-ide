# Relay

Reach every pod of the user from any browser, a phone included, with nothing to install, no domain to buy and no network to configure: open `https://antennae.space`, pair once, see the projects of all the machines that are on. The relay only introduces the browser and the pods to each other; the traffic between them is end-to-end encrypted.

The IDE stays free and works without the relay (`127.0.0.1`, LAN, Tailscale). The relay is open source (MIT, like the rest) and self-hostable with every feature; the hosted one at `antennae.space` sells comfort only, close to a recurring donation with perks.

## Goals and non-goals

- **Simpler** than a VPN: no client on the phone (a PWA at most), no account form, no domain, no port to open.
- **Private**: the relay never sees code, terminals, settings or project names in clear; a compromised relay cannot impersonate a device.
- **Optional**: if the relay is down, local, LAN and Tailscale access keep working.
- Not a VPN: a tunnel for the IDE only (its protocol, HTTP previews and the HTTP services a pod chooses to share, see *Services*), not a network between machines.
- Not hosted machines: the user brings the machines.

## Pieces

```
                     ┌──────── relay (web-ide-pod relay) ────────┐
                     │ signaling · STUN/TURN · encrypted blobs   │
                     │ bootstrap page + Service Worker · push    │
                     └──▲──────────────────▲──────────────────▲──┘
            signaling   │                  │ outbound WS      │ outbound WS
                        │                  │                  │
 browser (phone) ═══ WebRTC DataChannels ═══ gateway pod ─── LAN ─── pod B
                        (DTLS, end to end)        ╚═══ WebRTC ═══ pod C (other cluster)
```

- **Relay**: a subcommand of the pod binary, `web-ide-pod relay`, with its SQLite base. Signaling (WebSocket), STUN and TURN (Pion TURN, embedded), storage of encrypted blobs, the bootstrap page, Web Push. Hosted at `antennae.space`; anyone can run their own and point their pods to it.
- **Pod**: keeps one outbound WebSocket to its relay (no port to open), answers WebRTC offers with Pion, and serves its usual protocol over DataChannels.
- **Browser**: loads a small bootstrap page and a Service Worker from the relay; everything else comes from the user's own pods through the tunnel.

## Transport

- WebRTC with ICE: direct paths first (host, then STUN hole punching), TURN relay when they fail (symmetric NAT, mobile CGNAT, UDP blocked). TURN is also offered over TCP/TLS 443 for corporate networks.
- The DTLS fingerprints of both sides are bound to the proofs signed inside the DataChannel (see *Identity*): a relay that swaps the offer changes a fingerprint, so a signature fails and the connection is refused. No extra signaling format is needed for that.
- TURN credentials are short-lived (HMAC with an expiry) and given by the relay to authenticated devices only, with a quota per account: never an open relay.
- **DataChannels**: one reliable, ordered channel carries the current JSON protocol unchanged (requests, responses, events); each terminal and each file transfer gets a channel of its own, so a big upload never delays a key stroke.
- The protocol is versioned: every channel opens with a `hello { protocol, version }`; a pod too old or too new for its gateway is listed with *Update this pod* instead of its projects.

## Where the code of the page comes from

- On a machine with a pod, the user keeps opening `http://127.0.0.1:4433`: the page comes from the local pod, which acts as the gateway to the others — their pages live under `/_lan/pod/<key>/` of that origin, over the LAN or pod to pod over WebRTC.
- Elsewhere, `antennae.space` serves only a **bootstrap**: a small, auditable page and a Service Worker. Once a tunnel is up, the Service Worker fetches the application from the pod over the DataChannel. When a project opens, its front end comes **from the pod that holds it**, under `/pod/<key>/` of the relay origin, so a front end always speaks to its own pod, whatever the versions of the others (switching to a project of another machine reloads the page).
- **The assets the pod says are immutable are cached by the Service Worker** (#71): one cache per pod and per build of its front end (`webide-assets:<key>:<build>`, the version when the pod tells no build), read before a fetch is sent through the tunnel, written only for what the pod answers with `Cache-Control: immutable`, under a cap of 8 MB per entry (the 26 MB speech runtime is streamed, never kept). A pod that declares a new build drops its old cache; a cache older than a month is dropped when the Service Worker starts. `/api` calls and previews always go through the tunnel.
- **The page of the pod is cached under its build** (#73): the pod tells the fingerprint of its front end (a hash of its `index.html`, which names every asset by its hash) in the `$hello` of its handshake and in its register, and marks its page with `X-Webide-Build`. The Service Worker keeps a page only when that header matches the build the window declared, under the exact URL it answered: a development rebuild keeps its version, never its build. The frame opens only once the tunnel is up, so a cached page never stands for a live connection.
- **The shell of the relay is cached** (#73): the bootstrap page, its scripts and styles, the identity module, the wordlist, the manifest and the icons, precached by the Service Worker in `webide-shell:<hash>`. The relay writes that hash into `sw.js` (a hash of the files it serves), so a deploy that changes the shell changes the Service Worker; the browser checks it on every navigation and installs the new one in the background. The first Service Worker takes over at once; a newer one waits while a page runs on the old shell, which shows a **Reload** bar — a reload cuts the tunnels of the page, so the user chooses when. A reload of the page therefore fetches nothing from the relay but `sw.js` and its links: it pays the signaling, ICE and the handshake, no static file (e2e `relay`: 0 channels, 0 bytes through the tunnel on a reload). With the relay down, the cached page says so instead of the browser's error page.
- **The connection says what it does** (#74): under the current step (Relay, Pod, Secure handshake), the card shows the sub-step it waits for and since when — signaling link, TURN credentials, the pod's answer, ICE with the candidates of each side, the path chosen (direct, or relayed by TURN and over which transport), DTLS, the proofs. A **Details** panel, open by default, keeps every event with its time and copies it (no token, key nor SDP in it). The app adds the end of the load (#75) — its script started, its first message from the pod, its home page shown — and the journal stays readable once the app is open: Settings > Remote access > Connection journal, and `window.bootJournal` in the console of the page. A sub-step that waits too long (10 s for the signaling link, 15 s for the answer, the DTLS channel and the handshake, 30 s for ICE) says what blocks and its likely cause, with Retry, while the page keeps waiting. The pod logs the same steps of each tunnel: `relayclient: tunnel <session>: offer received`, `answer sent after …, N candidates (the later ones trickled)`, `ICE connected, pod relay/udp ↔ browser host/udp`, `handshake done (device <name>)`.
- **One WebSocket, and the offer in parallel** (#75): the page signals its tunnels on its identity link (`/_relay/identity`): `{type:"signal", pod, session}` opens a session and the relay answers its ICE servers, then `offer`, `candidate` and `bye` go as on `/_relay/signal`, and every message of a session carries it (the identity module hands them to their tunnel, never to a waiter of the link). The signaling needs no proof, as `/_relay/signal` does not; the relay carries it even while it waits for the proof of possession of the link. The link opens as the page starts, beside the device store and the session of the device — with the pod of the link (or the one opened last) in its URL, `/_relay/identity?pod=<id>&session=<s>`, so the relay opens that session and sends its ICE servers as the link comes up — and the offer to the pod of the link, or the one opened last, leaves as soon as both are ready; its handshake waits for the pods list to know the device key that must answer, and the tunnel is dropped for a new one if that list names another entry. `/_relay/signal` stays for the token mode before its link, pods dialing pods and the load generator.
- **Candidates are trickled both ways** (#75): a pod answers an offer — and a pod dialing another one sends its offer — with the candidates it gathered within 50 ms (host and reflexive ones come in milliseconds; the TURN allocations of a pod took ~180 ms from an iPhone), and sends the later ones (a TURN allocation that takes longer) as `candidate` messages after its description, never before it. It used to wait for its whole gathering, up to 8 s. A peer that reads no trickled candidate still has the quick ones in the SDP. A candidate of the browser that arrives before its offer is set is kept until then. On the wire a pod's candidate is the JSON of the candidate as a string (what the page parses); a pod reads both that and the object a browser sends.
- The WebSocket client of the front end goes through a transport interface: a WebSocket on `127.0.0.1`, the DataChannel through the relay.
- App previews (`localhost:3000` of a pod) go through the Service Worker and a DataChannel as well.
- Later: a signed, versioned bootstrap so that even the hosted relay cannot change it silently.

## Identity

No e-mail, no password. An account is a key. **Done** (`pod/internal/identity`, `web-ide-pod pair`, Settings > Remote access > Members): see *Milestone 2* below.

- **Recovery phrase**: 24 BIP39 words, made on the first device and shown **once**, with a check that the user wrote it down (like a hardware wallet). It is never stored by the IDE, on disk or in the relay: storing it would turn the theft of one machine into the theft of the account. The user may keep it in a password manager.
- From the phrase (HKDF): the **account key** (Ed25519, its public half is the account id) and the **sync key seed**.
- **Member keys**: each browser and each pod makes its own key pair and gets a **certificate** signed by the account key: device public key, name, kind (browser, pod), date, `scope` (always `all` for now: the field exists so that read-only or per-project devices need no new format). A pod stores its key in `~/.web-ide/device.key` (0600). On the wire and in storage a member is still called a device (the `devices` message, the `device` fields, `device.key`, `identity.json`, the text `device revoked`), as it was before the glossary, so that releases keep talking; the code says so where it matters.
- **Admin devices** hold the account key (encrypted at rest; in a browser, unlocked by a passkey through the WebAuthn PRF extension) and can add and revoke devices. The others hold only their own key.
- **Passkeys** unlock the keys of the current browser day to day. A passkey is tied to a domain: each origin (`antennae.space`, a self-hosted relay, `127.0.0.1`) has its own.
- Every pod pins the account public key when it is paired and checks the certificate of every peer itself: it never trusts the relay to say who is who.
- **Recent browsers only** (decided): WebCrypto Ed25519 and the WebAuthn PRF extension are required, there is no fallback for older ones — the bootstrap page names what is missing. Chrome, Edge, Firefox and Safari of 2025 and later.
- **One origin per relay** (`antennae.space`, or the self-hosted one): accounts are isolated by keys, not by origins. Per-account subdomains would need wildcard DNS and TLS and hurt self-hosting, and a passkey is tied to an origin, so one passkey per origin per account (the user handle is the account id). The app runs on the relay origin, served only by pods paired with the account (trusted code); several accounts in one browser profile share that origin.
- **Passkeys and IndexedDB are per origin**: the tailnet address, `localhost` and the relay are separate devices, each enrolled once with the phrase. WebAuthn refuses an IP address as a relying-party id, so no passkey can be made on `127.0.0.1`: the Members panel lives on the relay origin and on `localhost`, and gives a one-click link to `localhost` when opened on `127.0.0.1`.

### Pairing

- **First pod**: `web-ide-pod pair create` makes the account (phrase shown once, three words asked back) or `pair restore` takes the phrase typed; `pair status` shows the device, the account and the fingerprints.
- **Another pod**: `web-ide-pod pair join` prints a code, a terminal QR and the 4-word fingerprint of its key, and waits for an admin — through the relay, or on the LAN when the pod has none (see *Local network*); `pair join --phrase` takes the phrase instead when no admin is around, and the pod keeps its own key (unlike `restore`, which gives it the admin key of the phrase).
- **A phone or a tablet**: scan the QR shown by an admin device (like WhatsApp Web) — the invite link `#join=<code>` opens the bootstrap page, which shows its own fingerprint and waits for the approval.
- **A computer**: the QR, or the phrase, whichever is easier.
- The code is 8 base32 characters, single use, 10 minutes; the 4-word fingerprint read on both sides is the guard against a relay that swaps the key. A code that already holds a key refuses another one.

### Revocation

An admin device signs a revocation list, stored by the relay and checked by every pod. `web-ide-pod pair revoke <key>` signs one from the phrase typed, offline; the pods pass a newer list on to each other over the LAN and to the relay. Revoking a device also rotates the sync key (next epoch, data encrypted again, new key wrapped for each remaining device) and suggests renewing the API keys of the vault, since a key that leaked stays leaked.

The relay stores the list only when its signature verifies against the account it names and its `seq` is higher than the stored one, and pushes it to the online devices of the account; a relay that replays an older list changes nothing. The panel (Settings > Remote access > Members) lists the devices of the account with their kind, date and fingerprint, approves a request by its code after comparing the fingerprint, shows the invite QR, and revokes.

### Formats

- **Phrase**: 24 BIP39 words (256-bit entropy, embedded English wordlist, checksum). Seed = BIP39 PBKDF2 seed; HKDF-SHA256 (32-byte zero salt) gives the account Ed25519 seed (`info "web-ide account v1"`), the sync seed (`"web-ide sync v1"`) and the device seed (`"web-ide device v1"`). The account id is the base64url of the account public key.
- **Certificate**: canonical JSON `{v:1, account, key, name, kind: browser|pod, created, scope: "all"}` + the Ed25519 signature of the account key, base64url. Fixed field order, no spaces: the browser and the pod build the same bytes, checked by the shared test vectors (`pod/internal/identity/vectors.json`, run by `make test` in Go and in JS).
- **Revocation list**: `{account, seq, epoch, revoked: [keys], created}` signed by the account key; the revoked keys are sorted so both sides build the same bytes; a higher `seq` wins.
- **Fingerprint**: the 4-word reading of a key id (44 bits of its SHA-256, 11 bits per word), shown on both sides of a pairing.

### Handshake v2 (cert mode)

The same shape as the M1 token handshake, with Ed25519 signatures instead of the HMAC of the token, each side signing `role|fpBrowser|fpPod|nonceBrowser|noncePod` with its device key:

```
browser → $hello { protocol, version: "2", nonceB, cert }
pod     → $hello { …, nonceP, cert, sig = Ed25519(podKey, "pod"|fpB|fpP|nB|nP) }
browser → $auth  { sig = Ed25519(browserKey, "browser"|fpB|fpP|nB|nP) }
pod     → $ready
```

Each side checks the other's certificate against the **pinned** account key, the scope `all` and the revocation list. A swapped offer changes a fingerprint, so a signature fails: the connection is refused. The errors are `unpaired`, `cert` (a paired pod refuses the token mode), `foreign`, `revoked`, `proof`; failed proofs are still rate-limited and the handshake keeps its 10 s deadline.

The **token mode** of M1 (`#t=`) stays for unpaired pods, and `127.0.0.1` is unchanged (token cookie). A paired pod refuses the token mode through the relay.

## Multi-pod

**Done** (#58 `pod/internal/multipod`, `relay/clusters.go`: proof of possession, clusters, election, encrypted project lists, unified home page; #59: routing to every pod, see *Routing (one origin)* below; #60: protocol versions and *Update this pod*, see *Versions and updates* below).

- **Proof of possession**: `register` on the pod link and on the identity link is answered by a `challenge {nonce}`; the device signs `relay|<relay origin>|<nonce>` with the key its certificate names, and the relay only accepts the proof of that key. A copied certificate therefore registers nothing, and a device that proves nothing gets no presence and no gateway role (it stays in the plain token mode of M1). The binding is `identity.RelayBinding`, so a proof made for one relay does not work at another.
- **Clusters**: each pod reports the peers its LAN control links reach (`cluster {peers: [device keys]}`, at register and on every change of a link). The relay takes the connected components of the reported edges among the online devices of the account — an edge counts when one end reports it and both ends belong to the account — and calls each component a **cluster**, named by its smallest device key. A pod that sees nobody is a cluster of its own.
- **Election**: one **gateway** per cluster — the pod marked *preferred* (Settings > Remote access > *Preferred gateway*, `gateway.preferred` in `config.json`, `-preferred` flag), else the one online since the longest (`since`, ties by key). A gateway whose link drops without a `bye` keeps the role for 10 s, so a flapping link moves nothing; the role moves on a clean leave. The relay pushes `gateway {cluster, key}` to the pods of the account and to the identity links, and the presence `pods {key, podId, name, version, cluster, gateway, since}` to the identity links (the bootstrap page picks its entry point there).
- **Encrypted project lists**: each pod publishes `projects:<its device key>` in the blob store of milestone 4 — `{v, pod, name, version, updated, projects: [{id, title, description, type, path, icon}]}`, the icon being the SVG the pod keeps, capped at 8 KB per project and the whole blob under the size cap. A pod with no link of its own sends its sealed record to a peer (`$blob` on the control link), which forwards it **unchanged**: the relay checks the signature of the device that wrote it, so the hop adds no trust. The relay caches ciphertext only and answers a `blobGet` of the kind prefix `projects:` with every blob of the account. **The pod decrypts** (the gateway first, since the browser opens its tunnel there): the relay never sees a project name, and a dump of its base shows none.
- **Unified home page**: `multipod.Directory` merges three views — the LAN peers first (their page is served under `/_lan/pod/<key>/`, and they work with the relay down), then the presence the relay reports, then the pods whose only trace is a cached list (offline, greyed, *seen {time} ago*). A pod that published nothing this pod can read is listed with *waiting for the sync key*, which is not an error. RPC `pods.list`, event `pods.changed`. Each project carries its icon (from the published list, also for a LAN peer whose live `projects.list` has none) and its last opening (`opened` in the list, Unix seconds; a pod broadcasts `projects.changed` when a project is opened, so the lists follow): the page merges every pod's projects into one list (see the spec, *Home page and projects*). Its actions on a project of another pod (`projects.update`, `projects.delete`, `projects.icon.save`, `projects.create`, `workspace.get`/`workspace.dirs`/`ssh.info` for the form) are requests to that pod on a side channel (`web/src/pod/remote.ts`): `rpc:home` on the relay origin (own tunnel, or routed through the gateway), the WebSocket of `/_lan/pod/<key>/ws` on a pod; kept 30 s after its last answer.
- A pod may set its LAN address by hand when discovery gets it wrong.
- **Bootstrap without `#pod`**: after unlock the bootstrap page asks the identity link for the presence, then opens the **gateway** of the cluster last used (`localStorage`, `webide.relay.site`), else of the first cluster; with no pod online it lists the certificates of the account, greyed. `#pod=` still works.
- **Wake-on-LAN, shutdown, reboot, restart**: see *Power* below.

### Routing (one origin)

**Done** (#59). A project of any pod opens **with the front end of the pod that holds it**, on **one origin**: no port, no subdomain, so the installed PWA shows no bar of an outside cluster.

- **On the relay origin**, the pages of a pod live under `/pod/<device key>/`, mirroring `/_lan/pod/<device key>/` on the origin of a pod. The Service Worker of the relay routes a request by its prefix to the tunnel of that pod (`{kind:'http', pod, url, base}`) and answers the app, its assets, the previews and the `/api` calls of the page.
- **A pod registered at the relay** is reached **directly**: the bootstrap keeps one tunnel per pod (`tunnels: Map<key, {pc, rpc}>`), opened on demand when the page asks a port (`askPort(label, base)`), and closed when idle. The handshake v2 is checked by the browser against the certificate of the pod it names.
- **A LAN-only pod** (no link of its own) goes through the **gateway of its cluster**: the bootstrap labels its channels `@<key>/<label>` on the tunnel of the gateway, which hands them to the peer over `/_lan/tunnel?w=<window>&label=<label>` (`lan/tunnel.go`, `relayclient.OnForeignWrap` → `multipod.Route`). Its page keeps the URL `/pod/<key>/…` of the relay origin, with `base: /pod/<key>` carried in the `http:<n>` channel, so the front end builds its own URLs.
- **On `127.0.0.1`** the local pod is the gateway (whatever the election). A key that is not a LAN peer is reached **pod to pod over WebRTC** (`relayclient.Dial`): the pod behaves as a browser on the signaling link, offers with Pion, and `multipod.RemoteGateway` serves `/_lan/pod/<key>/` with one `http:<n>` channel per request and the page WebSocket bridged to `rpc`. The token cookie is checked locally and dropped for the remote pod.
- **Trust is hop by hop**, each hop checking the certificates: browser ↔ pod over DTLS (handshake v2 bound to the two SDP fingerprints); gateway ↔ LAN peer over the control link (v2 bound to the TLS leaf fingerprints, `transport(fp)` pinning); gateway ↔ remote pod over DTLS as a browser would. A routed channel carries the **window id** of the browser, so the gateway signs the handshake of the end pod with the certificate it verified itself (`X-Webide-Via` on `/_lan/tunnel`, `via` in the `$hello` of `Dial`): the end pod rechecks it against **its own** revocation list and refuses a browser the gateway would still accept. The gateway sees the routed traffic in clear — end-to-end encryption of the routed hops is #57.
- **Failover**: the bootstrap watches the tunnel of its entry. When it closes it asks the presence again (`pods` on the identity link), picks the new gateway of the cluster it was on (`routes.js`) and reconnects with backoff, showing *Reconnecting through {name}…*. The Home iframe moves to `/pod/<new gateway>/`; a page of a LAN-only pod keeps its URL, its channels are re-bridged through the new gateway and the app re-attaches its terminals from their offsets (#19). Pages of directly tunneled pods are untouched. On `127.0.0.1` nothing changes: the local pod is the gateway.
- **Back from sleep** (#76): a phone that sleeps leaves its tunnel open on its side while the pod closes it (ICE failed). When the page shows again after 5 s hidden (also `pageshow`, `online`), the app sends `client.lang` and, with no answer within 4 s, posts `stale` to the bootstrap, which drops the tunnel at once. A tunnel that drops while its pod is still listed is dialled again to that same pod first, and the iframe is **not** reloaded: the bootstrap ends every port of the old tunnel with a `null` message (WebKit may not fire `close` on a MessagePort), the app takes its channels again and `pod.reconnected` refreshes its state, so the page and what is being typed stay. The frame moves only when the entry pod changed. The draft of the assistant box is also kept in `sessionStorage`, for a tab the phone discarded and reloads whole.
- **A link to a page of a pod** (`/pod/<key>/…` opened in a tab of its own: the link Claude Code gives, a new tab) is sent to the bootstrap page as `/#open=<that path>`, by the Service Worker or, before it is installed, by the relay; the bootstrap opens the path as is in its frame, since the app only runs there. `/open?path=&line=` asked through the tunnel sends the frame on to the project page under the path of the pod, without asking the windows of other devices. The Service Worker carries the query of a request to the pod, and follows a redirect of the pod.
- The routing decisions of the bootstrap (which gateway, own tunnel or routed, which prefix) live in `relay/web/routes.js` as pure functions, run headlessly by `scripts/routes-test.mjs` (`node --test`, part of `make test`).

### Versions and updates

**Done** (#60, `multipod/version.go`, `identity/update.go`, `pod/internal/update`, `lan/update.go`).

- **Protocol version**: `multipod.Protocol` (an int) is the contract of everything the pods of an account exchange — the LAN control protocol, the signaling messages of the relay, the shape of the project lists and of the settings blobs. It is told in `$info` of a LAN link, in `register` of the pod link and in the `projects:` list, and carried in the `pods` presence; a pod that says nothing speaks protocol 0, the one of the pods older than #60. The home page of a pod compares each version with its own: *older version* / *newer version*.
- **Never routed across a gap**: `lan.ServeGateway`, `lan.OpenTunnel` and the pod-to-pod `Dial` refuse a mismatched peer, and the relay elects the gateway of a cluster among the pods that speak the protocol of the cluster (the majority, the highest version on a tie). A cluster is never carried by a pod that would not understand it. The app lists the projects of a mismatched pod without a link: *{name} runs another multi-pod protocol: update it*.
- **Update this pod**: the home page of a pod running a release offers an outdated pod the version it runs itself (`pods.self` → `canUpdate`, `identity.IsReleaseTag`; a build of the source tree reports a development version, which no pod installs). The **browser signs** `{v, pod, version, created}` with its device key (`identity.js` `signUpdate`; the canonical form is one of the shared vectors, so the page and the pod agree on every byte the signature covers).
- **The pod it names decides**, whoever carried the request: `$update` on the LAN control link, `update` on the pod link, and the relay — a plain carrier — routing it to the online pod of its account the request names, with the id of the request rewritten to a **hop id** of its own so no other pod can answer for it. `identity.CheckUpdate`: the certificate of the signer belongs to the account this pod pinned, is not revoked and is a browser or pod device; the request names this pod; the version is a release tag; `created` is fresh (5 min). A request already run is refused. The reason reaches the page.
- **Detached**: the pod runs `~/.local/lib/web-ide/install.sh <version>` — the copy `scripts/install.sh` leaves next to the binary it installed — through `systemd-run --user` when it is the systemd user service, `setsid` otherwise, so the restart the installer triggers does not kill the installer. It answers `running` before it exits. A pod that does not run as the service answers `not_service` with the command to run there by hand (`scripts/install.sh <version>`), which the block shows. `WEBIDE_UPDATE_CMD` stands for the installer in the tests.
- A pod listed as *newer version* is the one to update, and the page offers nothing from it: what a pod can offer is the version it runs itself.

### Power

**Done** (milestone 7, `identity/power.go`, `pod/internal/power`, `relay/power.go`). The home page wakes a pod that sleeps, and restarts, reboots or shuts down one that runs, from any device of the account — a phone on the relay origin included.

- **Signed like an update**: the browser signs `{v, pod, action, created}` with its device key (`identity.js` `canonicalPower`, a shared vector), `action` being `wake`, `shutdown`, `reboot` or `restart`. `identity.CheckPower` makes the checks of `CheckUpdate` (certificate of the pinned account, not revoked, signature, 5 min) and refuses an unknown action; a signature already run is refused.
- **No passkey on the LAN**: a window on the WebSocket of the pod itself (its token, or `127.0.0.1`) already holds the terminals of the machine, and through its LAN links those of the other pods: it sends the action unsigned (`pods.self` says `local`), and the pod signs it with its own device key, which the pod that acts checks the same way. A window that came through the relay or a gateway (`ServeTunnel`) must sign: an unsigned request from it is refused.
- **Carried like an update**: the pod the page talks to runs a request for itself; for another pod it sends `$power` on the LAN control link, else `power` on the pod link, which the relay carries to the pod it names with a hop id (`power.done` comes back). The pod it names decides.
- **Shutdown and reboot are off by default**: the pod runs as the user, and `sudo web-ide-pod allow-shutdown [-user U] [-remove]` writes `/etc/polkit-1/rules.d/50-web-ide.rules` (and `/etc/web-ide/allow-shutdown`, which names the user: polkit keeps the folder of its rules to itself, so the pod reads that file to know whether to offer Shut down), which lets that user call the `power-off` and `reboot` actions of logind (with other sessions open and with inhibitors: the pod runs `systemctl poweroff -i`). Without the rule the pod refuses with the command to run, and the page shows it. `scripts/install.sh` prints that command at the end. The action starts one second after the answer, so the answer reaches the page.
- **Restart** restarts the systemd user service through `systemd-run --user` (a unit of its own, as for an update); a pod started by hand answers `not_service`. The terminals survive when the keeper runs them.
- **Wake-on-LAN**: each pod publishes in its project list (`wake: [{mac, net}]`, `power: bool`) the cards a magic packet can wake — up, not the loopback, not `docker*`, `br-*`, `veth*`, `virbr*`, `tailscale*`, `tun*` — and whether its rule is installed; it also tells both in the `$info` of its LAN links, so a LAN peer that publishes no list through the relay is covered, and an offline peer keeps what it told. A machine cannot be woken from the internet without a device awake on its network: the pod the page talks to sends the packet itself when it has an address in a network of the sleeping pod (UDP port 9, to the broadcast address of that network and to 255.255.255.255); otherwise it sends `power` with `wake` to the relay, which asks **every other online pod of the account** and passes back the first `sent` (or the refusal, *no awake pod is on the network of that machine*). The wake is signed too: the pod that sends the packet checks it, since the target sleeps. LAN peers are not asked: they are on the network of the pod that asked.
- **Under WSL** (`power/wsl.go`, a Windows machine that stays on and wakes the others): the networks of the WSL 2 virtual machine are not the LAN (NAT), and its broadcast does not leave it. The pod reads the IPv4 networks of Windows too (`Get-NetIPAddress` through `powershell.exe`, once a minute at most) and sends the packets through `powershell.exe` (a .NET `UdpClient`, same addresses and port); it publishes no card of its own, the ones it sees being virtual. `powershell.exe` is looked up in the `PATH`, else at its place on `C:` (a systemd service gets no Windows `PATH`).
- **The card**: `allow-shutdown` also prints the Wake-on-LAN state of the wired cards (`ethtool`) and, with NetworkManager, the command that keeps it on (`nmcli connection modify <c> 802-3-ethernet.wake-on-lan magic`). The BIOS (or UEFI) setting is the user's.
- **The page**: an offline pod with a card shows **Wake**, then *Waking…* until it is back online (3 min at most); a pod that runs shows a power menu (*Restart the pod*, *Reboot*, *Shut down*, each confirmed), the last two disabled with the command in their tooltip when its machine has no rule. A pod older than these requests publishes neither field and is offered nothing. `WEBIDE_POWER_CMD`, `WEBIDE_POWER_ALLOWED`, `WEBIDE_WAKE_IFACES` and `WEBIDE_WAKE_PORT` stand for systemctl, the rule, the cards and port 9 in the tests.

## Local network

**Done** (#50, `pod/internal/lan`). The pods of one account reach each other on the LAN with no relay at all — no internet, no relay configured, or the relay down.

- **LAN port**: a paired pod opens a TLS port of its own (`:4436`; `-lan`, `lan.addr` in `config.json`, `off`). An unpaired pod opens none. The certificate is self-signed (`lan.crt`, `lan.key`) and serves as both the server and the client certificate: TLS only encrypts, trust comes from the handshake.
- **Handshake**: the handshake v2 of the tunnel on `/_lan/hello`, the dialing pod in the browser role, bound to the two TLS leaf fingerprints instead of the DTLS ones. A machine in the middle that shows its own certificate makes a signature fail. The peer must be a `pod` certificate of the pinned account, not revoked; the token mode is refused.
- **Control link**: the hello WebSocket stays open (pings every 15 s). Both pods tell their name, version and LAN port (a pod that was dialed dials back) and pass their revocation lists on: a newer list spreads from pod to pod and goes to the relay as soon as a pod of the account reaches it (pod link `revocations`), so a list signed offline is never undone by the next one an admin signs from the relay's copy. While the link is up, the LAN port serves the HTTP and WebSocket requests that carry the peer's TLS certificate as requests of the machine itself.
- **Discovery**: mDNS / DNS-SD `_web-ide._tcp` with `pod` (a hash of the device key) and `acct` (a hash of the account id, not the id: the announcement cannot be followed from one network to the next); nothing secret. Only the announcements of the account's tag are dialed. Addresses typed by hand (`lan.peers`, Settings > Remote access > Local network) for another subnet or a network without multicast; the reason an address fails is shown (no answer, another account, revoked, proof, another version).
- **Gateway**: the local pod serves the page of each peer under `/_lan/pod/<device key>/` of its own origin, a reverse proxy pinned to the peer's TLS certificate. One origin keeps the installed app (PWA) in its window, with no bar of an outside cluster. The local pod checks its token cookie, then the proxy drops it and the peer trusts the certificate instead. The same handler serves a peer to a **browser tunneled through the relay**: `/_lan/pod/` of the tunnel is routed to it, and `/_lan/tunnel` carries the channels of a window of the relay origin (see *Routing*). The home page of a peer is never shown under its prefix: the page goes to the home page of the pod that serves it (`web/src/app/home.ts`; on the relay origin the bootstrap answers `{kind: 'entry'}` with the base of its entry pod). The home page of the local pod lists the projects of each peer (its `projects.list`, kept fresh over a WebSocket of the protocol, and the *clusters* of *Multi-pod* are made of these links).
- **Pairing without a relay**: `pair join` serves its request on its LAN port (`/_lan/join`, announced by mDNS with a `join` code, or its address typed by hand). A paired pod that finds it shows it in the Members panel: with no relay, the pod answers the panel's link (`/_relay/identity`) itself, with the same messages — the devices it knows, the joining pods, revocations passed on. The admin browser signs the certificate, the pod posts it to the joining pod (pinned to the TLS certificate it read), which checks it is for its own key.
- Limits: inviting a phone by QR needs the relay.

## Services

**Planned.** A pod shares a local HTTP service (Ollama, the web UI of a cooling daemon, SearXNG) with the other pods of the account, which reach it on a port of their own machine: `curl 127.0.0.1:11434` on moon answers from the Ollama of astra, through the LAN or the relay. HTTP only (WebSockets and streamed answers included): no raw TCP, no Unix socket, and Docker is left to the Docker tool of the IDE.

- **Published by hand**: the home page has a *Services* section; the pod lists what it shares, each with a name and a port of its machine (`127.0.0.1:<port>`), and can turn one off or delete it. Nothing is shared by default. Kept by the pod (`services.json` in `~/.web-ide`), not by a project. The pod publishes `services: [{id, name}]` in its encrypted project list and in the `$info` of its LAN links (no port, no address), so every pod of the account sees them.
- **Linked on demand**: the other pods list these services, each with a switch that turns its link on or off. Turning a link on opens a listener on the machine of the pod that asked: the port of the service by default, the next free one when it is taken (shown), or one typed by hand; scope *this machine* (`127.0.0.1`, default) or *local network* (`0.0.0.0`, with the warning of the SSH port forwards: anyone on the network reaches the service with no authentication, and Ollama has none). A link that is on stays on — no window needed, kept across a restart of the pod — until it is turned off. Kept in `service-links.json`.
- **Transport, the LAN first**: the listener is a reverse proxy; each request goes to the pod that shares the service over its LAN port (TLS pinned, the peer's certificate as identity) whenever it is a LAN peer, and only otherwise pod to pod over WebRTC through the relay (one `http:<n>` channel per request, the WebSocket bridged like the gateway's). The route is chosen per request, so a link moves to the LAN as soon as the peer shows up there, and back to the relay when it leaves, without being turned off.
- **Connection on demand**: a link that is on only holds its listener. The WebRTC connection opens at the first request (about a second, more through TURN) and closes after 10 minutes with no request nor open WebSocket; the next request opens it again. The LAN link of the peer is already there and costs nothing. Answers are streamed as they come (an Ollama generation shows token by token). The service sees `127.0.0.1:<port>` as its host, like a preview. Through TURN the bytes count in the quota of the account.
- **The pod that shares decides**: a request names the service and comes from a pod certificate of the pinned account, not revoked; the service must exist and be on. Starting a link **attaches** it on that pod first (`services.attach`); a request of a pod that is not attached is refused.
- **The route is always shown**, on both sides, as a badge: **LAN** (direct on the local network), **Relay · direct** (WebRTC, direct or hole-punched path), **Relay · TURN** (copied by the relay, counted in the quota), or **idle** (on, no connection open for now). The tooltip gives the addresses of the pair.
- **Open links, both sides**: the pod that shares lists the pods attached to each service (name, route, since when, requests, bytes, last request) with *Cut*, which detaches that pod: its link shows *cut by {pod}* and turns off. The pod that links lists its links (service and pod, switch, route, local address as a link, state — *{pod} offline, retrying*, *cut by {pod}*, *port taken* — requests, bytes). A link whose pod goes offline keeps its listener and answers 502 *{pod} is offline* until it is back.
- **Later**: the services of a pod in a browser with no pod (a phone on the relay origin, `/pod/<key>/svc/<id>/`); many web UIs break under a sub-path, so it waits for a need.

## Settings sync

**Done** (#28, `pod/internal/settingsync`, Settings > Remote access > Sync). The settings live in each pod (`settings.json`, shared by its browsers), so **the pods sync**, the browsers don't. The relay stores one encrypted blob per account and kind (`settings`, `vault`) and never sees a value; the pods do the merge.

- **Sync key**: the key of an epoch is `HKDF(syncSeed, "web-ide sync epoch <e>")`, so a device that knows the phrase can always rebuild it, nothing random to lose; each kind takes a sub-key of it. Every blob is AES-256-GCM with a random nonce per write and the associated data `account|kind|epoch|seq`: a blob cannot be moved to another account, kind, epoch or seq.
- **Wrap**: a pod paired by an admin does not know the phrase, so it cannot derive the key. Each pod makes an X25519 key from its device seed and publishes `{device, x25519, sig}` signed by its device key; the admin browser (Members panel) wraps the epoch key for it (X25519 + HKDF + AES-GCM) and posts the wrap. A pod with no wrap has no key and never writes. The wrap is made at approval and at each rotation. Go and JS read the same test vectors (`pod/internal/identity/vectors.json`, run by `make test` in both languages).
- **Storage**: the `blobs`, `wraps` and `synckeys` tables (`PRAGMA user_version` migration), and on the pod link `syncKey`, `wrapGet`, `blobGet`, `blobPut` with compare-and-swap on `seq` (a write is refused when it is not `stored + 1`), a size cap per blob, and the stored write pushed to the online pods of the account. Every write is signed by the device key and checked against the account and the revocation list: a revoked device cannot write.
- **Merge**: each entry carries its value, the hybrid logical clock of the change that wrote it and the device that made it; a pod keeps the last state it synced (its base, `sync/base-<kind>.json`). An entry changed on the other side and untouched here is taken, an entry changed here and untouched there stays, and only an entry changed on both sides to different values asks the user: the page shows both values and which device, and the choice is a normal write. Maps (`tokenColors`, `syntax`, `keyboard.overrides`, `devices`, the vault entries) merge per key, and paths unknown to the pod are kept. Every applied change goes through `Settings.Save` with a label (`sync from <device>`), so the history and the rollback keep working. A pod writes on each local save and catches up at reconnect.
- **Per device**: the fonts and the panel sizes belong to a device (`devices[<id>]` in the settings, `sizes[<id>]` in the sessions), so a phone keeps its layout on any pod of the account. A device without its own entry uses the *fallback layout* the user saves in Settings.
- **Vault** (opt-in, its own blob kind and its own key): the API keys of the model servers (by server id) and the remembered passwords (`secrets.json`), merged per entry. Off, nothing is put and the blob is deleted. After a revocation the Members panel suggests renewing the API keys and lists the servers that hold one: a revoked device could still read the vault until the epoch moves.

## Push notifications

**Done** (milestone 6: `pod/internal/push`, `relay/push.go`, Settings > Notifications). The **pod** decides when to notify, since the page may be closed, and encrypts the payload for the subscription of the browser (RFC 8291, aes128gcm); the **relay** holds the VAPID key, signs (RFC 8292) and POSTs the ciphertext to the push service. The relay sees an endpoint and ciphertext, never a title or a project name.

- **Installable app**: the relay serves the manifest and the icons of the pod's front end (`web/public`, one copy), linked by the bootstrap page, whose footer offers **Install the app** when Chromium hands it its install prompt, and says *Share › Add to Home Screen* on iOS (#73); the Service Worker shows a notification from the decrypted JSON `{title, body, url, tag}` and, on a click, moves the app of that pod's bootstrap window to the path (`/#pod=<id>&open=/project/<id>?chat=<id>` or `?ticket=<n>`), or opens a new window. The bootstrap page remembers the last pod, so the installed app starts at `/`. iOS shows notifications only from the installed app: the settings say so when `Notification` or `PushManager` is missing.
- **Relay**: the VAPID P-256 key is made once in its data folder (`vapid.json`, 0600), its public half at `/_relay/push/key`. A browser registers its endpoint (`POST /_relay/push/subscribe`) with its certificate and the Ed25519 signature of its device key over `web-ide push v1|subscribe|<endpoint>|<created ms>` (10 minutes at most): the certificate must verify against its account and not be on the relay's revocation list. It gets an opaque id (`push_subs (id, account, device, endpoint, created)`); `unsubscribe` is signed the same way. Only the endpoints of the push services of the browsers are taken (FCM, Mozilla, Apple, WNS, https on the default port; `-push-test-endpoint` adds a prefix for the tests), and the POST follows no redirect: no open proxy, no request into the relay's network.
- **Pod link**: `push.send {sub, body, ttl, urgency, topic}` is taken only from a pod that registered with a certificate of its account the relay checked, for a subscription of that account, within 30 a minute per account. `404`/`410` from the push service deletes the subscription and tells the pod (`push.gone`); revoking a device deletes its subscriptions. Nothing of the payload is stored or logged.
- **Pod**: `push.json` (0600) keeps, per browser device, the relay's id, the keys of the subscription, a switch per kind and the language of its texts (RPCs `push.status`, `push.subscribe`, `push.unsubscribe`, `push.settings`, `push.test`). The kinds: **assistant finished** (a run of a root conversation ends by itself), **assistant asks** (an approval, a question, a plan), **tests failed** (the task of a saved command flagged `test` ends with a code that is not 0, whoever started it: the Console, the assistant, the MCP), **ticket feedback** (added by the assistant or Claude Code, not by the user). A device whose window on this pod is visible (`window.visible`, sent by the page with its device) gets nothing; the toasts of the page are there. The `Topic` is the conversation (or the ticket), so a burst of turns leaves one notification.
- **Every pod of the account** (#59): a browser subscribes on the pod it shows, then the app repeats `push.subscribe` and the per-kind `push.settings` on **each pod of `pods.list`**, on a side rpc channel of its own (`rpc:push`, asked to the bootstrap page with the base of that pod — its own tunnel, or the window `@<key>/rpc` of the gateway). The subscription and the switches are kept on the origin (`localStorage`, `webide.push`), so a pod that shows up later is re-subscribed when the browser next connects to it, and *Disable* clears every pod.
- **Settings > Notifications** (on the relay origin, paired): *Enable on this device* (the permission, `pushManager.subscribe` with the relay's key, the signed registration, then `push.subscribe` here and on every pod), a switch per kind, *Send a test*, *Disable*.

The e2e `push` suite replaces the subscription of the browser with one whose keys it made, runs the fake push service it points to (VAPID checked, body decrypted in Node), hands the payload to the Service Worker (CDP `ServiceWorker.deliverPushMessage`) and clicks the notification; it also checks that the relay base and log hold no title nor project name. The `multipod` suite enables notifications on one pod and checks that an assistant turn run on a pod of **another cluster** notifies that browser.

## Share links

A public HTTPS link to a port of a pod, to show a work in progress to a friend: `https://<random>.share.antennae.space`.

- The relay ends TLS with its own Let's Encrypt wildcard certificate and forwards to the pod, which calls the local server in HTTP, or in HTTPS accepting a self-signed certificate. Unlike the tunnel, the relay sees this traffic in clear: the user is told.
- Short-lived (24 h by default, 7 days at most), a secret in the URL, a password unless the visitor's address is allowed, a bandwidth quota, revoked from the IDE at any time.
- Before opening them on the hosted relay: legal notice, terms, privacy policy, an abuse contact and a way to cut a link at once (the relay is a host under the LCEN and the DSA). A self-hosted relay leaves this to whoever runs it; the documentation says so.

## Shared sessions (later)

Code and review together:

- A link with an ephemeral guest key; the guest picks a nickname, no account. The host accepts or refuses, chooses read-only or editing, and can switch it during the session. The terminal is a separate permission, asked each time.
- Several carets in the editor; the pod is the authority: browsers send their changes with the version they saw, the pod rebases and broadcasts them (the model of `@codemirror/collab`, simpler than a CRDT).
- Voice over WebRTC, on the connection that already exists.
- Guests run on another origin than the application, so code served to a guest can never read the keys of the account.

## Hosted service and pricing

The hosted relay runs on one EU VPS (`antennae.space`, OVH VPS-1): `web-ide-pod relay` with its own systemd service, its own user and its own data folder (`/var/lib/antennae`: the base, the VAPID key, the ACME cache). The domain is served by the binary itself — Let's Encrypt through `autocert` (TLS-ALPN-01 on 443, the cache in `<data>/acme`), `:80` redirecting to https — and everything listens on both stacks (IPv4 and IPv6). See [self-hosting](../howto/self-host-relay.md) for running your own.

Everything else — relay, pairing, multi-pod, settings sync, the vault, push — is **free at every level**.

An organization whose third-party access policy refuses the OAuth app answers 403: the window says so, and `relay team admin <org> <login>` names the admin by hand.

One-time: $5 is a Supporter for 30 days, $10 a VIP for 90 days, $50 a VIP for 360 days. Everything else is free.
- Share links (planned, *Share links* above) stay a perk from Supporter up; shared sessions and voice may come later.
- Between two tiers the lower one counts ($7 a month is a Supporter, $49 once a VIP for 90 days). Two sponsorships of one person do not add up: the base keeps one row per sponsor, the best live level (then the one that lasts longer), and a monthly tier change replaces the monthly row. So a $2 Backer who pays $10 once is a VIP for 90 days, then reads free until the hourly read of the list brings the monthly row back.
- **The VIP list** (`vips` table, dbVersion 8): the admin of the relay makes people VIPs by hand, by **GitHub login** (resolved once to its id by `GET /users/<login>`, so a renamed login keeps it) or by **account id** (no GitHub link, nor GitHub app: a self-hosted relay uses it too), with an optional end and a note only the admin sees (no message carries it). An ended row no longer counts and stays listed until removed. `web-ide-pod relay vip add|remove|list` and `web-ide-pod relay supporters` (everyone at Backer level or above: level, source, end, linked accounts, note) read and write `relay.db` directly, next to the live relay; `make vip ARGS=…` and `make supporters` run them on the hosted one over SSH.
- **Felt without reconnecting**: a GitHub link, a webhook and the hourly read tell the pods of the accounts at once (`tellQuota`). A row the CLI writes comes from another process: the relay reads `PRAGMA data_version` every 30 s on a connection held for it (the value is per connection), recomputes the levels when it moved or when an end passed, and tells only the accounts whose level changed — its own writes (the TURN usage every minute) move the version too, and must not send every pod a message. `QuotaState` and the `github` answer of the identity link carry `level`, `until`, `sponsor` (the level of the sponsorship alone) and `vip`; `supporter` stays (true from Supporter up) for the older pods and panels.
- Paid through GitHub Sponsors: the account links a GitHub login (an OAuth app asked with **no scope** — it only proves who the person is), and the relay checks the sponsorship against its cached sponsor list (read with the maintainer token once an hour through GraphQL — `viewer.sponsorshipsAsMaintainer`, past and private sponsorships included, since Sponsors has no REST API — and moved one row at a time by the `sponsorship` webhook: `created` and `tier_changed` set the tier, `cancelled` drops a monthly sponsorship at the end of its paid period, the `pending_*` events change nothing). No e-mail is ever asked by the IDE, and **the relay never keeps a user token**: the link is `account → GitHub id`, nothing else. Paddle may come later for people without GitHub.
- **GitHub setup** (once, as the maintainer), written to `/etc/antennae/env` (0640, `root:antennae`) then `systemctl restart antennae-relay`: an **OAuth App** (not a GitHub App) whose callback is `https://<domain>/_relay/github/callback`, no device flow, no expiring tokens (`WEBIDE_GITHUB_CLIENT`, `WEBIDE_GITHUB_SECRET`); a **classic token** with the `read:user` scope alone, which reads the sponsor list (people only: an organization cannot link an account, and reading its id would need `read:org`) (`WEBIDE_GITHUB_TOKEN`; note its expiry: past it, no new supporter is seen); the **webhook of the Sponsors dashboard** to `https://<domain>/_relay/github/webhook`, content type `application/json`, with a secret (`WEBIDE_GITHUB_WEBHOOK`). The relay logs `relay: github sponsors: …` when a read fails, and keeps the cached list.
- **The quota counts every TURN allocation of the key**: browser ↔ pod and pod ↔ pod (milestone 3 dials one PeerConnection per window and remote pod). The bytes are counted in the relayed path itself (a counter per allocation, no lock per packet), written to the base per key and month, and read back with what is live right now. Over the quota, the relay issues no TURN credential: the direct and STUN paths keep working, the page and Settings say the quota is reached and point at what raises or lifts it. Credential TTL is 1 h so a new level is felt quickly and a quota is not outrun by a long session.
- A self-hosted relay has every feature without limits (`-quota` unset).
- **Counting**: the relay keeps anonymous counters only — `/_relay/status` answers up, version, uptime, pods online and accounts seen in the last 30 days; no telemetry in the pod or the page.
- **Deploy**: `make deploy-relay` puts the current tree on it (Linux x86_64 build, installed to `/usr/local/bin/web-ide-pod`, `antennae-relay` restarted, the Service Worker served checked against the build, the previous binary kept for `RELAY_ROLLBACK=1`); `RELAY_VERSION=v1.11.0` deploys a published release with its checksum. `make deploy-relay RELAY_SETUP=1` (`deploy-relay.sh --setup`) writes the host itself — user, data folder, unit with the flags of the hosted relay (`-quota 10GB -quota-backer 20GB`: a unit written before #87 has no `-quota-backer`, so a Backer gets twice `-quota`, the same 20 GB, until `RELAY_SETUP=1` rewrites it), firewall, unattended upgrades, nightly backup timer — and is idempotent. The data of the relay is never touched.
- **Capacity**: a session costs four TURN allocations (each end asks for a relay address over UDP and over TLS 443, taken while it gathers even when the tunnel ends direct), so the `-turn-ports` range is the first wall: the 2840 ports of the hosted relay (`20000-22839`, below the ephemeral range of the kernel) carry about 710 simultaneous sessions. `make load-relay` measures it on a second instance of the same host, and [load tests](load.md) holds the numbers.
- **Backups and uptime**: the host backs its base up nightly (`sqlite3 .backup` + the data folder, kept 14 days); `scripts/relay-watch.sh --pull`, on a machine of the user, copies them off-cluster (30 days kept) and `--status` checks `/_relay/status` every 10 minutes (`--timers` installs both).

## Milestone 1 (done)

Three pieces, one binary:

- **`web-ide-pod relay`** (`pod/internal/relay`): signaling over WebSocket, STUN and TURN (Pion TURN, UDP and TCP, and TURN over TLS on 443 shared with HTTPS through an ALPN demux, `stun.turn`; a client that names no protocol, as Pion does, is routed by its first bytes after the handshake), the bootstrap page and the Service Worker, a SQLite base (`pods`, `usage`, `PRAGMA user_version`). Short-lived HMAC-SHA1 TURN credentials (1 h, so a quota and a change of level are felt quickly), given only to a registered, online pod.
- **The pod** (`pod/internal/relayclient`): one outbound WebSocket to its relay (`-relay` flag or `relay` in `config.json`), pod id and secret in `relay.json` (0600) of the data folder, backoff reconnect, one PeerConnection per offer, trickle ICE with the ICE servers announced by the relay. The remote link is printed at startup and shown in Settings > Remote access with its state.
- **The browser**: the bootstrap page and the Service Worker come from the relay; the app, its assets and the previews come from the pod through the tunnel. The front end talks to a `Transport` (`web/src/pod/transport.ts`): a WebSocket on `127.0.0.1`, or a MessagePort to the bootstrap page. Each project window gets its own connection.

**Channels** (`pod/internal/tunnel`): the JSON protocol is unchanged on the `rpc` channel; `term:<id>` carries the input and output of one terminal, `xfer:<n>` one big message, `http:<n>` one HTTP request of the Service Worker. Every message is framed into 16 KB fragments (1-byte header: 1 = more, 0 = last) so a 2 MB transfer stays under the DataChannel cap, with back-pressure.

**Access control in this step** is the pod token, and the relay never sees it. The token is proved inside the DataChannel and bound to both DTLS fingerprints (channel binding), so a relay that swaps the SDP cannot MITM:

```
browser → $hello { protocol, version, nonceB }
pod     → $hello { protocol, version, nonceP, proof = HMAC(token, "pod"|fpB|fpP|nonceB|nonceP) }
browser → $auth  { proof = HMAC(token, "browser"|fpB|fpP|nonceB|nonceP) }
pod     → $ready
```

The fingerprints are read from the `a=fingerprint` line of each SDP; failed proofs are rate-limited per pod, and the handshake has a 10 s deadline. A protocol mismatch answers `$hello { error: "version" }` and the bootstrap page shows *Update this pod*. Identity (phrase, device certificates, pairing) came with milestone 2: the token mode stays for unpaired pods, and a paired pod refuses it.

What is not in this step: multi-pod and gateways, encrypted blob storage, push, quotas. A pod with no relay, or whose relay is down, keeps working on `127.0.0.1` (the e2e `relay` suite checks both, with TURN forced and the pair asserted as a relay one).

## Milestone 2 (done)

The identity of *Identity* above, in three places:

- **`pod/internal/identity`**: BIP39 (generate, validate, checksum), the derivation, the certificates, the revocation lists, the verification of a peer certificate. The pod identity in the data folder: `device.key` (0600) and `identity.json` (its own certificate, the pinned account key, the last revocation list). The wordlist and the test vectors are embedded; `scripts/identity-vectors.mjs` runs the same vectors in JS, so a signature made in the browser verifies in the pod.
- **`pod/internal/identity/web/identity.js`**: the same formats in JS, imported at runtime by the bootstrap page and by the app (served under `/_relay/identity.js` by the relay and by the pod — one copy, so the two sides cannot disagree on the bytes a signature covers). The device key is made with WebCrypto Ed25519 and stored wrapped by an AES-GCM key derived from the passkey (WebAuthn PRF), unwrapped as a non-extractable key for the session. That key is kept an hour after its last use (a separate IndexedDB, `webide-session`: `keepUnlocked`, `resume`, `touch`, `lock`), so a reload or the installed app opening again does not ask the passkey; never the seed, the PRF, the account key or the sync seed, so an admin action still asks it. *Lock* (the bootstrap page, Settings > Remote access > Members) ends it, and a revoked device drops it.
- **`web-ide-pod pair`**: `create`, `restore`, `join`, `status` (see *Pairing*). The relay keeps the identity tables (`accounts`, `devices`, `pairings`) to list the devices and route pairing; it never holds a private key or the phrase, so it can check a signature against an account id but never make one — only a device holding the account key can approve a pairing or push a revocation list.
- **Settings > Remote access > Members**: the admin panel, on the relay origin and on `localhost` (see *Identity*). The pod only carries the frames of the pairing link.

The identity works **without a relay**: `pair create`, `restore` and `status` run offline, `identity.json` and the certificate checks do not depend on `relayclient`, and the handshake v2 proof takes the two peer fingerprints as plain inputs — so the LAN link (#50, *Local network*) feeds it the TLS certificate fingerprints of a direct WebSocket instead of the DTLS ones.

The e2e `identity` suite pairs a pod with the CLI and two browsers (a virtual authenticator answering the WebAuthn PRF), and checks that an unpaired browser and a revoked one are refused; the swapped-offer refusal is a Go integration test with Pion peers and a relay that rewrites the SDP.
